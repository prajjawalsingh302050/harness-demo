How this demo works

A tiny app with one table of 10,000 people, deliberately unhealthy. A GitHub Action runs sensors against the code and the live app, a Gemini coding agent fixes what fails and opens a pull request, a human merges it, Vercel redeploys, and the sensors run again until every check is green.

1. SensorsScan the code and load-test the live app
→
2. Health reportEach result is compared with budgets.json
→
3. Coding agentGemini edits the code; tests must pass
→
4. Pull requestA human reviews and merges
→
5. DeployVercel ships it; the loop runs again

Setup

FrontendPlain HTML, CSS and JavaScript in public/, served by Vercel's CDN. Pages: index.html people list · person.html lookup by ID · health.html health report · architecture.html this page
BackendFastAPI on one Vercel Python function. api/index.py creates the app and the timing middleware, app/routes.py has the endpoints, app/db.py runs every SQL query.
DatabaseSQLite file data/shop.db, read-only: one table people (id, name, email, city), 10,000 rows.
Endpoints GET /api/people?limit=N up to 5000 people · GET /api/people/{id} one person · GET /api/health liveness
ObservabilityEvery response carries X-DB-Queries and Server-Timing. Queries slower than 5 ms are logged.
