How this demo works

This shop is deliberately unhealthy. A GitHub Action runs sensors against the code and the live app, a Gemini coding agent fixes what fails and opens a pull request, a human merges it, Vercel redeploys, and the sensors run again until every check is green.

1. SensorsGitHub Actions scans the code and load-tests the live app
→
2. Health reportEach result is compared with budgets.json
→
3. Coding agentGemini edits the code; tests must pass
→
4. Pull requestA human reviews and merges
→
5. DeployVercel ships it; the loop runs again

Frontend

TechnologyPlain HTML, CSS and JavaScript. No framework, no build step.
HostingStatic files in public/, served by Vercel's CDN
Pages index.html orders dashboard · user.html customer lookup · health.html latest health report and history · architecture.html this page
Scripts js/api.js fetch helper that reads X-DB-Queries and timing · js/app.js orders table and paging · js/user.js customer lookup · js/health.js reads reports from the health-reports branch via the GitHub API · js/config.js repository settings
Stylingcss/style.css, light and dark mode via prefers-color-scheme

Backend

TechnologyFastAPI (Python 3.12)
HostingOne Vercel Python function (FastAPI preset), entry point api/index.py
DatabaseSQLite file data/shop.db (2,000 users, 20,000 orders, 160,000 order items), opened read-only. Built from migrations/*.sql by scripts/build_db.py.
Endpoints GET /api/orders?page=N 50 orders with customer and total · GET /api/users/{id} one customer and order count · GET /api/health liveness
ObservabilityMiddleware adds Server-Timing: db;dur, app;dur and X-DB-Queries to every response. Queries slower than 5 ms are logged as slow query.
